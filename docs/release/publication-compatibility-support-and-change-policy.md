## Intended first prerelease channel

The intended first prerelease publication channel is a future, separately
authorized GitHub Release in `CNTX-PROJECT/CNTX`, marked as a prerelease. Its prospective Release
Version and tag representation are `0.1.0-prealpha.1` and

This channel statement is intent only. It creates no GitHub Release, active

Repository visibility, a branch, a merge to `main`, or a tag alone is not a
release publication. Only an exact separately authorized and verified release

## Exact publication subject and set

A future release decision must pin:

- the exact repository commit and tree;
- the exact Release Identity and Release Version;
- the exact immutable tag name and target;
- every included repository path and every excluded path or material class;
- any generated archive, manifest, BOM, SBOM, digest, signature, attestation,
  or other release artifact, if separately authorized;
- the exact GitHub repository and Release record;
- the intended audience, limitations, security/privacy/legal/disclosure
  basis, and unsupported claims; and
- the correction and withdrawal procedure applicable to that channel.

Nothing may be silently included from repository issues, pull requests,
mutable settings, a working tree, private repository, local context store,
ignored file, mutable alias, external cache, private or restricted material,
private implementation, private vulnerability report, provider-internal state,
future state, or future commit. Generated
artifacts must be reproducibly bound to the exact authorized source or remain
explicitly absent.

REMEDIATE-002 selects no final release subject or publication set and
authorizes no generated artifact.

## Tag and release-record integrity

A published tag must be immutable and target the exact commit authorized by
the release decision. The GitHub Release record must identify the same tag,
Release Version, subject, limitations, and publication scope. Mutable aliases
such as `latest` do not define normative identity, precedence, compatibility,
or support.

Automatic source archives generated by a hosting platform are derived channel
representations, not independent normative sources. Their existence does not
expand the authorized publication set or create a compatibility or support
claim.

## Compatibility boundary

Compatibility is multidimensional. Contract, schema, Serialization Binding,
Schema Resource, validation, evidence, Artifact Instance, implementation,
release, and support compatibility remain separate. A statement about one
dimension cannot be generalized to another.

For a pre-alpha release:

- only the exact Accepted identities and versions included in the selected,
  version-pinned public subject are within scope;
- no compatibility with a previous or future version is promised;
- no backward, forward, universal, runtime, provider, API, CLI,
  implementation, Artifact Instance, validator, interoperability, product, or
  support compatibility is implied;
- Semantic Versioning syntax does not itself prove compatibility; and
- incompatible change is permitted in a later separately governed version if
  it is attributable, documented, and does not rewrite history.

Any future compatibility claim must name its exact dimensions, versions,
subjects, evidence, evaluator or implementation context, limitations, and
authority. Missing or unverifiable evidence fails closed and remains visible.

## Support and audience boundary

The prospective `0.1.0-prealpha.1` release is unsupported pre-alpha material
intended for documentation and JSON Schema users to inspect as public review
and experimentation material only, without suitability or implementation
warranty. It creates no:

- supported-version line, maintenance duration, end-of-life date, update
  cadence, support channel, response target, service level, or warranty;
- production-readiness, security, privacy, legal, compliance, reliability,
  performance, availability, fitness, or suitability claim;
- certification, accreditation, compatibility badge, score, grade, or quality
  gate; or
- implementation, validator, resolver, registry, API, CLI, workflow, runtime,
  provider, or product commitment.

The responsible-disclosure route in [Security](../../SECURITY.md) remains the
sole vulnerability-reporting route, is separate from a support service, and
does not imply remediation timing or a supported release line.

## Change, correction, and withdrawal

Material changes require a new attributable commit and, where applicable, a
new Release Version. A historical release subject, version, tag, and record
must not be silently replaced, rewritten, or moved.

A future correction, withdrawal, deprecation, supersession, channel change,
or exceptional security removal must:

1. retain the original historical record;
2. identify the exact affected release, subject, scope, reason, and known
   impact that may be publicly disclosed;
3. preserve private vulnerability and other restricted-information boundaries;
4. identify the replacement, mitigation, or absence of one;
5. distinguish correction, deprecation, withdrawal, and support status; and
6. record known cache and mirror persistence limits; and
7. carry separate attributable EIGENAAR / Final Authority authorization for
   every consequential action.

This Accepted policy executes no correction or withdrawal and creates no
promise that either will occur within a particular period.

## Claim and final-authority boundary

Publication evidence, assessment, remediation, review, release recommendation,
release approval, release decision, tagging, publication, compatibility
claim, support commitment, correction, withdrawal, distribution, and
deployment are distinct lifecycle events.

Only a later separate attributable EIGENAAR / Final Authority decision may
authorize an exact Release Version, tag, GitHub Release, publication set, and
consequential action. This policy grants no such authority and does not resolve
ASSESS-002 responsibility 10.
